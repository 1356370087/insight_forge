# 我们如何构建多智能体研究系统

我们的 Research 功能使用多个 Claude agent 来更有效地探索复杂主题。本文将分享我们在构建这个系统过程中遇到的工程挑战，以及从中获得的经验教训。

![](https://www-cdn.anthropic.com/images/4zrzovbb/website/094d7021ebd5cf57eabd63b456899c97f5231c88-1000x1000.svg)



Claude 现在已经具备 [Research 能力](https://www.anthropic.com/news/research)，可以在 Web、Google Workspace 以及各种集成工具中进行搜索，从而完成复杂任务。

这个多智能体系统从原型走向生产环境的过程，让我们在系统架构、工具设计和提示词工程方面获得了重要经验。**多智能体系统由多个 agent 组成，这些 agent 本质上是能够在循环中自主使用工具的 LLM，它们共同协作完成任务。** 我们的 Research 功能包含一个 agent，它会根据用户查询规划研究流程，然后使用工具创建并行 agent，让它们同时搜索信息。包含多个 agent 的系统会引入新的挑战，例如 agent 协调、评估和可靠性。

这篇文章将拆解那些对我们有效的原则。我们希望这些经验能在你构建自己的多智能体系统时有所帮助。



### 多智能体系统的优势

研究工作通常涉及开放式问题，很难提前预测完成任务所需的步骤。探索复杂主题时，无法硬编码一条固定路径，因为这个过程本质上是动态的，并且依赖于此前的探索路径。当人们进行研究时，通常会根据新的发现不断调整方法，并沿着调查过程中出现的线索继续深入。

这种不可预测性使 AI agent 特别适合研究任务。研究需要在调查推进过程中具备灵活转向的能力，或者探索与主题间接相关的联系。模型必须能够在多轮交互中自主运行，并根据中间发现决定接下来应该追踪哪些方向。**线性的、一次性的流水线无法处理这类任务**。

搜索的本质是压缩：从庞大的语料库中提炼洞察。Subagent 通过并行运行并拥有各自的上下文窗口来促进这种压缩。它们可以同时探索问题的不同方面，然后将最重要的 token 压缩后交给 lead research agent。每个 subagent 还提供了关注点分离：不同的工具、提示词和探索轨迹。这减少了路径依赖，并支持更全面、彼此独立的调查。

一旦智能达到某个阈值，多智能体系统就会成为扩展性能的重要方式。例如，尽管单个人类在过去 10 万年中变得更加聪明，但人类社会在信息时代变得**指数级**更强大，是因为我们的**集体**智能和协作能力。即使是具备通用智能的 agent，作为个体运行时也会面临限制；而 agent 群体能够完成更多事情。

我们的内部评估显示，多智能体研究系统尤其擅长广度优先查询，这类查询需要同时追踪多个相互独立的方向。我们发现，在内部研究评估中，以 Claude Opus 4 作为 lead agent、Claude Sonnet 4 作为 subagent 的多智能体系统，比单智能体 Claude Opus 4 的表现高出 90.2%。例如，当系统被要求识别信息技术类 S&P 500 公司中的所有董事会成员时，多智能体系统通过将任务拆解给 subagent 找到了正确答案，而单智能体系统由于搜索缓慢且顺序执行，未能找到答案。

多智能体系统之所以有效，主要是因为它们可以投入足够多的 token 来解决问题。在我们的分析中，有三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估中 95% 的性能方差。BrowseComp 用于测试浏览型 agent 定位难以查找的信息的能力。我们发现，token 使用量本身就解释了 80% 的方差，另外两个解释因素是工具调用次数和模型选择。这个发现验证了我们的架构：将工作分发给拥有独立上下文窗口的 agent，从而为并行推理增加更多容量。最新的 Claude 模型会成为 token 使用效率的巨大倍增器，因为升级到 Claude Sonnet 4 带来的性能提升，比将 Claude Sonnet 3.7 的 token 预算翻倍还要更大。**对于超出单个 agent 能力边界的任务，多智能体架构可以有效扩展 token 使用量。**

但也存在一个缺点：在实践中，这类架构会很快消耗大量 token。在我们的数据中，agent 通常使用的 token 约为聊天交互的 4 倍，而多智能体系统使用的 token 约为聊天的 15 倍。要具备经济可行性，多智能体系统需要应用在任务价值足以覆盖性能提升成本的场景中。此外，某些领域要求所有 agent 共享相同上下文，或者 agent 之间存在大量依赖关系，目前并不适合多智能体系统。例如，与研究相比，大多数编码任务中真正可以并行化的任务更少，而 LLM agent 目前还不太擅长实时协调和向其他 agent 委派任务。我们发现，多智能体系统尤其适合那些高价值任务：需要大量并行化、信息量超过单个上下文窗口，并且需要与众多复杂工具交互。



### Research 的架构概览

我们的 Research 系统采用多智能体架构，使用 orchestrator-worker 模式。在这种模式下，lead agent 负责协调流程，同时将任务委派给并行运行的专业化 subagent。

当用户提交查询时，lead agent 会分析查询、制定策略，并生成 subagent，让它们同时探索不同方面。如上图所示，subagent 充当智能过滤器，通过迭代使用搜索工具来收集信息。在这个例子中，subagent 会研究 2025 年的 AI agent 公司，然后向 lead agent 返回公司列表，使 lead agent 能够整理最终答案。



使用检索增强生成（Retrieval Augmented Generation，RAG）的传统方法通常采用静态检索。也就是说，它们会获取一组与输入查询最相似的 chunk，并使用这些 chunk 生成响应。相比之下，我们的架构使用多步骤搜索，可以动态找到相关信息，适应新的发现，并分析结果以形成高质量答案。

这张流程图展示了我们的多智能体 Research 系统的完整工作流。当用户提交查询时，系统会创建一个 Lead Researcher agent，并进入迭代式研究流程。

1. Lead Researcher 首先思考研究方法，并将计划保存到 Memory 中，以持久化上下文。这样做是因为如果上下文窗口超过 200,000 个 token，就会被截断，因此保留计划非常重要。
2. 随后，它会创建具有具体研究任务的专业化 Subagent（图中展示了两个，但实际可以是任意数量）。每个 Subagent 会独立执行 Web 搜索，使用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 评估工具结果，然后将发现返回给 Lead Researcher。
3. Lead Researcher 会综合这些结果，并判断是否需要更多研究。如果需要，它可以创建额外的 subagent，或者调整研究策略。一旦收集到足够信息，系统就会退出研究循环，并将所有发现传递给 CitationAgent。
4. CitationAgent 会处理文档和研究报告，识别具体的引用位置。这样可以确保所有的论断都被正确归因到对应来源。最终，包含引用的研究结果会返回给用户。



### 研究型 agent 的提示词工程与评估⭐

多智能体系统与单智能体系统之间存在关键差异，其中包括协调复杂度的快速增长。早期 agent 会犯一些错误，例如为简单查询生成 50 个 subagent、无休止地在 Web 上搜寻不存在的来源，或者通过过多更新相互干扰。由于每个 agent 都由提示词引导，因此提示词工程是我们改善这些行为的主要杠杆。下面是我们在 agent 提示词设计中学到的一些原则：

1. <strong>像你的 agent 一样思考</strong>。 要迭代提示词，就必须理解提示词会产生什么影响。为了帮助我们做到这一点，我们使用 [Console](https://console.anthropic.com/) 构建了模拟环境，并使用与系统中完全相同的提示词和工具，然后逐步观察 agent 的工作过程。这立刻暴露了失败模式：agent 在已经获得足够结果后仍继续执行、使用过于冗长的搜索查询，或者选择了错误工具。有效的提示词设计依赖于对 agent 建立准确的心智模型，这会让最具影响力的改动变得显而易见。

2. <strong>教会 orchestrator 如何委派任务</strong>。 在我们的系统中，lead agent 会将查询拆解为子任务，并将这些任务描述给 subagent。每个 subagent 都需要一个目标、一种输出格式、关于使用哪些工具和来源的指导，以及清晰的任务边界。如果缺少详细的任务描述，agent 就会重复工作、留下缺口，或者无法找到必要信息。一开始，我们允许 lead agent 给出简单、简短的指令，例如"研究半导体短缺问题"。但我们发现，这些指令往往过于模糊，导致 subagent 误解任务，或者执行与其他 agent 完全相同的搜索。例如，有一个 subagent 探索了 2021 年汽车芯片危机，而另外 2 个 subagent 则重复调查当前 2025 年供应链，没有形成有效分工。

3. <strong>根据查询复杂度调整投入</strong>。 Agent 很难判断不同任务需要投入多少努力，因此我们在提示词中嵌入了扩展规则。简单事实查找只需要 1 个 agent 和 3-10 次工具调用；直接比较可能需要 2-4 个 subagent，每个 subagent 调用 10-15 次工具；复杂研究可能需要超过 10 个 subagent，并且职责需要清晰划分。这些明确指南帮助 lead agent 高效分配资源，并防止在简单查询上过度投入，而这正是我们早期版本中常见的失败模式。

4. <strong>工具设计和工具选择至关重要</strong>。 Agent-工具接口和人机交互接口一样关键。使用正确工具非常高效，很多时候甚至是必要条件。例如，如果某些上下文只存在于 Slack 中，而 agent 却去 Web 上搜索，那么它从一开始就注定会失败。随着 [MCP server](https://modelcontextprotocol.io/introduction) 让模型能够访问外部工具，这个问题会进一步放大，因为 agent 会遇到此前未见过的工具，而这些工具描述的质量差异极大。我们给 agent 提供了明确的启发式规则：例如，先检查所有可用工具，将工具使用与用户意图匹配，使用 Web 搜索进行广泛的外部探索，或者优先使用专用工具而不是通用工具。糟糕的工具描述可能会把 agent 带到完全错误的路径上，**因此每个工具都需要有明确且独特的用途，并配备清晰描述**。

5. <strong>让 agent 改进自己</strong>。 我们发现 Claude 4 系列模型可以成为出色的提示词工程师。**当给定一个提示词和一个失败模式时，它们能够诊断 agent 为什么失败，并提出改进建议**。我们甚至创建了一个工具测试 agent：当给它一个有缺陷的 MCP 工具时，它会尝试使用该工具，然后重写工具描述以避免失败。通过对工具进行数十次测试，这个 agent 发现了关键细节和 bug。这种改善工具易用性的流程，使未来使用新描述的 agent 的任务完成时间减少了 40%，因为它们能够避免大多数错误。

6. <strong>先广泛探索，再逐步收窄</strong>。 搜索策略应该模仿人类专家的研究方式：先探索整体图景，再深入具体细节。Agent 往往默认使用过长、过于具体的查询，导致返回结果很少。我们通过提示 agent 从简短、宽泛的查询开始，评估可用信息，然后逐步收窄重点，来抵消这种倾向。

7. <strong>引导思考过程</strong>。 [Extended thinking mode](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking) 会让 Claude 在可见思考过程中输出额外 token，可以作为可控的 scratchpad。Lead agent 使用 thinking 来规划方法，评估哪些工具适合任务，判断查询复杂度和 subagent 数量，并定义每个 subagent 的角色。我们的测试表明，extended thinking 改善了指令遵循、推理和效率。Subagent 也会先进行规划，然后在获得工具结果后使用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 来评估质量、识别缺口，并细化下一次查询。这使 subagent 能够更有效地适应任何任务。

8. <strong>并行工具调用会改变速度和性能</strong>。 复杂研究任务自然涉及探索大量来源。我们的早期 agent 会顺序执行搜索，速度非常慢。为了提升速度，我们引入了两种并行化方式：（1）lead agent 并行启动 3-5 个 subagent，而不是串行启动；（2）subagent 并行使用 3 个以上工具。对于复杂查询，这些改变最多将研究时间缩短了 90%，让 Research 能够在数分钟而不是数小时内完成更多工作，同时覆盖比其他系统更多的信息。

我们的提示词策略侧重于注入良好的启发式方法，而不是死板规则。我们研究了熟练的人类如何处理研究任务，并将这些策略编码进提示词中。这些策略包括：将困难问题拆分为更小任务、仔细评估来源质量、根据新信息调整搜索方法，以及识别何时应该侧重深度（详细研究某一主题）还是广度（并行探索多个主题）。我们还通过设置明确的 guardrail（护栏），主动缓解意外副作用，防止 agent 失控。最后，我们重点建立了带有可观测性和测试用例的快速迭代循环。



### 有效评估 agent⭐

良好的评估对于构建可靠的 AI 应用至关重要，agent 也不例外。然而，评估多智能体系统会带来独特挑战。传统评估通常假设 AI 每次都会遵循相同步骤：给定输入 X，系统应该沿着路径 Y 生成输出 Z。

但多智能体系统并不是这样工作的。即使起点完全相同，agent 也可能采用完全不同但同样有效的路径来达成目标。一个 agent 可能搜索三个来源，另一个 agent 可能搜索十个来源；它们也可能使用不同工具来找到同一个答案。由于我们并不总是知道正确步骤是什么，因此通常无法只检查 agent 是否遵循了我们预先规定的"正确"步骤。相反，我们需要更灵活的评估方法，用来判断 agent 是否达成了正确结果，同时是否遵循了合理过程。

**立即用小样本开始评估。** 在 agent 开发早期，改动往往会产生巨大影响，因为有大量容易获得的改进空间。一次提示词微调可能会让成功率从 30% 提升到 80%。当效应量如此之大时，只需要少量测试用例就能发现变化。我们从大约 20 个代表真实使用模式的查询开始。测试这些查询通常能让我们清楚看到改动的影响。我们经常听到 AI 开发团队推迟创建 eval，因为他们认为只有包含数百个测试用例的大规模 eval 才有用。然而，最好立刻用少量示例开始小规模测试，而不是等到能够构建更完善的 eval 后再开始。

**如果做得好，LLM-as-judge 评估可以规模化。** 研究输出很难用程序化方式评估，因为它们是自由形式文本，而且很少只有一个正确答案。LLM 天然适合给输出评分。我们使用了一个 LLM judge，根据 rubric 中的标准评估每个输出：事实准确性（论断是否与来源匹配？）、引用准确性（引用来源是否与论断匹配？）、完整性（是否覆盖所有被要求的方面？）、来源质量（是否优先使用一手来源，而不是质量较低的二手来源？），以及工具效率（是否使用了正确工具，并且调用次数合理？）。我们曾尝试使用多个 judge 来评估每个组件，但发现使用单次 LLM 调用、一个提示词，并输出 0.0-1.0 的分数和 pass-fail 等级，是最一致且最符合人类判断的方式。当 eval 测试用例**确实**有明确答案时，这种方法尤其有效，因为我们可以让 LLM judge 直接检查答案是否正确。例如，答案是否准确列出了研发预算排名前三的制药公司。使用 LLM 作为 judge，让我们能够可规模化地评估数百个输出。

**人工评估能够发现自动化遗漏的问题。** 测试 agent 的人会发现 eval 漏掉的边缘情况。这些情况包括异常查询上的幻觉答案、系统故障，或者细微的来源选择偏差。在我们的案例中，人工测试者注意到，早期 agent 经常选择经过 SEO 优化的内容农场，而不是权威但排名不那么靠前的来源，例如学术 PDF 或个人博客。向提示词中加入来源质量启发式规则后，有助于解决这个问题。即使在自动化评估的世界中，手动测试仍然必不可少。



多智能体系统具有涌现行为，这些行为并不是通过特定编程直接产生的。例如，对 lead agent 的小改动可能会不可预测地改变 subagent 的行为。成功需要理解交互模式，而不只是理解单个 agent 的行为。因此，这些 agent 的最佳提示词不只是严格指令，而是协作框架：它定义了分工、问题解决方法和 effort budget。要做好这一点，需要细致的提示词设计和工具设计、可靠的启发式方法、可观测性，以及紧密的反馈循环。你可以查看我们 Cookbook 中的 [开源提示词](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)，其中包含来自我们系统的示例提示词。



### 生产可靠性与工程挑战

在传统软件中，一个 bug 可能会破坏某个功能、降低性能，或者导致服务中断。而在 agentic 系统中，微小变更可能级联成巨大的行为变化，这使得为必须在长时间运行过程中保持状态的复杂 agent 编写代码变得异常困难。

**Agent 是有状态的，错误会不断累积。** Agent 可以长时间运行，并在大量工具调用之间保持状态。这意味着我们需要能够持久执行代码，并在执行过程中处理错误。如果没有有效缓解措施，微小的系统故障可能对 agent 造成灾难性影响。当错误发生时，我们不能简单地从头重启：重启成本高，而且会让用户感到沮丧。相反，我们构建了能够从 agent 出错位置继续恢复的系统。我们也利用模型自身的智能来优雅处理问题：例如，当某个工具失败时，让 agent 知道这个情况并允许它自行适应，效果出人意料地好。我们将基于 Claude 的 AI agent 的适应能力，与重试逻辑、定期 checkpoint 等确定性 safeguard 结合在一起。

**调试需要新的方法。** Agent 会做出动态决策，而且即使使用相同提示词，不同运行之间也具有非确定性。这让调试变得更困难。例如，用户会报告 agent"没有找到显而易见的信息"，但我们无法看到原因。是 agent 使用了糟糕的搜索查询？选择了质量较差的来源？还是遇到了工具故障？加入完整的生产 tracing 后，我们能够诊断 agent 为什么失败，并系统性地修复问题。除了标准可观测性之外，我们还监控 agent 的决策模式和交互结构，同时不监控单个对话的内容，以保护用户隐私。这种高层次可观测性帮助我们诊断根因、发现意外行为，并修复常见失败。

**部署需要谨慎协调。** Agent 系统是由提示词、工具和执行逻辑构成的高度有状态网络，几乎持续运行。这意味着每当我们部署更新时，agent 可能正处于流程中的任何位置。因此，我们需要防止出于善意的代码改动破坏已有 agent。我们不能同时把每个 agent 都更新到新版本。相反，我们使用 [rainbow deployments](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/) 来避免干扰正在运行的 agent，做法是在同时保持旧版本和新版本运行的情况下，逐步将流量从旧版本切换到新版本。

**同步执行会造成瓶颈。** 目前，我们的 lead agent 会同步执行 subagent，也就是等待每一组 subagent 完成后再继续。这简化了协调，但也在 agent 之间的信息流中制造了瓶颈。例如，lead agent 无法引导 subagent，subagent 之间也无法协调，而且整个系统可能会因为等待某个 subagent 完成搜索而被阻塞。异步执行能够带来额外并行性：agent 可以并发工作，并在需要时创建新的 subagent。但这种异步性会在结果协调、状态一致性和 subagent 之间的错误传播方面带来挑战。随着模型能够处理更长、更复杂的研究任务，我们预计性能收益将足以证明这种复杂性是值得的。



### 结论

构建 AI agent 时，最后一公里往往会变成大部分旅程。能在开发者机器上运行的代码库，要成为可靠的生产系统，需要大量工程工作。Agentic 系统中错误会复合累积，这意味着传统软件中的小问题可能会让 agent 完全偏离轨道。某一步失败可能导致 agent 探索完全不同的轨迹，进而产生不可预测的结果。基于本文描述的所有原因，原型与生产之间的差距通常比预期更大。

尽管存在这些挑战，多智能体系统已经被证明对开放式研究任务很有价值。用户反馈说，Claude 帮助他们发现了此前未曾考虑过的商业机会，梳理复杂的医疗健康选择，解决棘手的技术 bug，并通过发现他们独自无法找到的研究关联，最多节省了数天工作。通过细致工程、全面测试、注重细节的提示词和工具设计、稳健的运维实践，以及研究、产品和工程团队之间的紧密协作，多智能体研究系统可以在规模化条件下可靠运行，而这些团队也需要对当前 agent 能力有深入理解。我们已经看到这些系统正在改变人们解决复杂问题的方式。

## 附录

下面是一些关于多智能体系统的额外杂项建议。

**对跨多轮修改状态的 agent 进行终态评估。** 评估那些会在多轮对话中修改持久状态的 agent，会带来独特挑战。不同于只读的研究任务，每个动作都可能改变后续步骤的环境，从而产生传统评估方法难以处理的依赖关系。我们发现，关注终态评估而不是逐轮分析效果更好。与其判断 agent 是否遵循了某个特定过程，不如评估它是否达成了正确最终状态。这种方法承认 agent 可能会通过不同路径达成同一目标，同时仍能确保它们交付预期结果。对于复杂工作流，可以将评估拆分为离散 checkpoint，在这些 checkpoint 上检查是否发生了特定状态变化，而不是试图验证每一个中间步骤。



**长周期对话管理。** 生产环境中的 agent 经常参与跨越数百轮的对话，因此需要谨慎的上下文管理策略。随着对话延长，标准上下文窗口会变得不足，因此需要智能压缩和记忆机制。我们实现了一些模式，让 agent 在进入新任务之前总结已完成的工作阶段，并将关键信息存储到外部 memory 中。当上下文接近限制时，agent 可以生成拥有干净上下文的新 subagent，同时通过精心设计的 handoff 保持连贯性。此外，它们可以从 memory 中检索已存储的上下文，例如研究计划，而不是在达到上下文限制时丢失此前工作。这种分布式方法可以防止上下文溢出，同时保持长时间交互中的对话连贯性。



**让 subagent 输出到文件系统，以尽量减少"传话游戏"。** 对于某些类型的结果，直接使用 subagent 输出可以绕过主协调器，从而同时提升保真度和性能。与其要求 subagent 通过 lead agent 传达所有内容，不如实现 artifact 系统，让专业化 agent 可以创建独立持久化的输出。Subagent 调用工具，将它们的工作存储到外部系统中，然后把轻量引用传回协调器。这可以防止多阶段处理中的信息丢失，并减少通过对话历史复制大量输出带来的 token 开销。对于结构化输出，例如代码、报告或数据可视化，这种模式尤其有效，因为 subagent 的专用提示词生成的结果，通常比经过通用协调器过滤后的结果更好。
