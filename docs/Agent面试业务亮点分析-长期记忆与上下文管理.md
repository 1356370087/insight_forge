# Agent 面试业务亮点分析：长期记忆与上下文管理

## 一、业务亮点简述

深度研究 Agent 如果只依赖当前会话，会反复询问用户的语言偏好、项目技术栈和研究背景；如果把所有历史对话直接放回上下文，又会带来 Token 膨胀、陈旧信息污染和提示注入风险。

本项目基于 Mem0 构建了“观察—反思—画像”三层长期记忆，并把它接入研究主流程：

`会话上下文压缩 → 记忆召回 → 研究执行 → 最终报告 → 记忆提取与维护`

核心价值不是简单保存聊天记录，而是把长期记忆当成一套有信任边界、有版本、有生命周期的数据系统：

- 只从用户消息、明确项目上下文和通过证据门禁的研究结论中提取候选，不把原始网页、工具输出或最终报告直接写入记忆；
- 召回时综合相关性、重要性和时间衰减进行可解释排序，只向 Agent 注入当前有效的少量记忆；
- 通过重复检测、冲突判定、时态版本化、访问强化和软遗忘，减少矛盾或过期信息对后续研究的影响；
- 长会话达到模型上下文阈值时，压缩较早消息并保留完整研究摘要、系统消息和最近窗口，控制 Token 消耗。

## 二、核心设计说明

### 1. “观察—反思—画像”三层记忆

| 层次 | 保存内容 | 主要作用 |
|---|---|---|
| 观察 Observation | 用户研究偏好、领域背景、项目事实、可信研究结论 | 保存可追溯的原子事实，是后续推导的基础 |
| 反思 Reflection | 基于多条有效观察形成的高层结论，并记录来源记忆 ID | 从零散事实中识别稳定模式，避免每次研究重新归纳 |
| 画像 Profile | 沟通偏好、报告偏好、专业领域、重复主题和项目背景 | 为 Lead Agent 提供一份紧凑、统一的协作画像 |

反思不会递归使用其他反思作为输入，只基于有效观察生成。系统在未反思观察达到数量阈值、重要性总和达到阈值，或每日维护发现长时间未处理的观察时触发反思。画像在来源记忆发生变化时更新，并维护唯一的 canonical profile 和递增版本号。

### 2. 可信写入，防止“错误记忆永久化”

写入发生在最终报告生成之后，但代码只读取 Human Message，不读取 AI 回复、完整报告和原始搜索结果。候选还要经过置信度、类型白名单、长度、敏感凭据、URL、指令形文本和提示注入检测。

可信研究结论必须先进入已通过安全准入的 `evidence_registry`，置信度不低于 0.75，并满足“至少两个独立来源域名支持”或“存在权威度不低于 0.8 的来源”。写入时还要求候选结论与已验证 Claim 及其证据 ID 集合完全匹配，避免模型自行扩写结论。

### 3. 可解释召回与访问强化

召回仅由 Lead Agent 执行，并同时按用户、项目、应用、Schema 版本和 `active` 状态隔离。高级记忆采用以下应用侧评分：

`最终分 = 0.55 × 相关性 + 0.25 × 重要性 + 0.20 × 新鲜度`

新鲜度使用指数衰减，不同类型采用不同半衰期：用户偏好和领域画像默认 180 天，项目记忆与反思 90 天，可信研究结论 30 天。这样既能优先使用与当前问题相关的信息，也不会让高相似但已经过时的记录长期占据召回结果。

实际注入上下文的 v2 记忆会更新 `last_accessed_at` 和 `access_count`。访问次数不直接修改上述应用侧评分，但会影响软遗忘判断，使反复被使用的记忆更不容易归档。所有记忆都被包装为“不可信、仅供参考”的上下文，不能覆盖系统指令、权限和运行配置。

### 4. 冲突、时态版本与软遗忘

新观察写入前会与同类别的有效观察比较，并产生五种决策：

- `ADD`：独立的新事实；
- `NOOP`：重复或等价信息，不重复写入；
- `SUPERSEDE`：用户明确纠正旧事实，旧记录标记为已替代；
- `TEMPORAL_CHANGE`：新旧信息分别在不同时间成立，关闭旧记录有效期并建立替代关系；
- `CONFLICT`：暂时无法判断真伪，将相关记录放入同一冲突组，不擅自覆盖。

软遗忘采用归档而不是物理删除。只有低重要性、低访问次数、没有未决冲突、超过四个类别半衰期未触达且不是画像的记录才会被归档。归档和已替代记录默认不参与召回，但仍保留审计历史。

### 5. 会话内上下文压缩

长期记忆解决跨会话连续性，上下文压缩解决单次长任务的 Token 膨胀，两者职责不同。

当前实现会根据实际模型上下文上限计算阈值：消息接近上下文上限的 75% 时，Lead 或 Supervisor 将较早消息压缩成摘要，保留完整 System Message、完整 `research_brief` 和约占上下文 25% 的最近原始消息。切分时不会留下孤立的 Tool Message，而是保留对应的 AI Tool Call。

压缩摘要同样被标记为不可信上下文，并过滤凭据、角色伪造和提示覆盖等内容。这样既保留用户目标、关键决策、证据与未解决问题，也避免无限累积完整对话。

### 6. 面试时应说明的能力边界

基础记忆和高级记忆在源码中默认关闭，生产使用需要显式配置 Mem0 后端，并提供可信的 `user_id`、`project_id` 和 `app_id`。缺少租户边界时，系统会跳过召回和写入，不会落入共享默认空间。

记忆模块默认 `fail-open`：Mem0、反思或画像维护失败会记录指标并降级，但不会阻断最终研究报告。Platform 支持项目级 Decay 和全用户每日维护；OSS 仍保留应用侧评分与指定用户维护，但不具备完全相同的平台能力。

## 三、面试时的一分钟介绍

我主要解决的是研究 Agent 跨会话失忆，以及长任务上下文持续膨胀的问题。我没有直接保存完整聊天记录，而是基于 Mem0 设计了观察、反思、画像三层记忆：观察保存用户明确表达的偏好和项目事实，可信研究结论必须经过多来源或权威来源验证；反思从多条观察中提炼稳定模式；画像再形成唯一、紧凑的用户研究协作视图。召回时按相关性、重要性和时间衰减加权排序，并结合访问次数、冲突状态和时态版本控制记忆生命周期。低价值且长期未访问的记录只做软归档，不物理删除。对于单次长会话，Lead 和 Supervisor 在接近模型上下文上限时压缩旧消息，同时保护研究摘要、最近窗口和工具调用边界。这样既能延续个性化研究，又能降低陈旧信息污染和 Token 成本。

## 四、面试官可能提问及参考回答

### 问题 1：为什么不能直接把全部历史聊天存进向量库？

完整聊天中混有一次性任务、模型回复、工具噪声、过期结论和潜在提示注入。直接保存虽然实现简单，但后续高相似召回可能把错误信息重新注入 Agent。项目先提取结构化候选，再经过来源、置信度和安全规则过滤，保存的是可复用事实而不是原始对话。

### 问题 2：观察、反思和画像为什么要分三层？

观察负责保留可追溯的原子事实；反思负责从多条观察中发现稳定模式；画像负责把当前有效信息整理成 Agent 易使用的统一视图。分层后，推导结论仍能追溯到来源记忆，也可以在底层事实被纠正时重新生成画像。

### 问题 3：如何保证研究结论足够可信才写入长期记忆？

首先只接受已经通过安全准入的结构化证据；然后按 Claim 聚合，要求置信度达到 0.75，并由两个独立来源域名支持，或者至少有一个权威度达到 0.8 的来源。最终写入候选还必须与通过验证的 Claim 文本和证据 ID 完全一致，避免抽取模型改变原意。

### 问题 4：召回为什么不只看向量相似度？

相似度只能说明“像不像当前问题”，不能说明“值不值得用”和“是否已经过时”。因此项目把 Mem0 相关性与人工定义的重要性、指数时间衰减组合起来，输出三个分量和最终分，既便于调参，也便于解释某条记忆为什么被召回。

### 问题 5：用户偏好发生变化时怎么处理？

新观察会先与同类别有效记录比较。明确纠正时旧记录进入 `superseded` 状态；如果是随时间变化，则为旧记录设置 `valid_to`，新记录设置 `valid_from` 并保存替代关系；无法确定时建立冲突组，而不是让模型任选一个覆盖。

### 问题 6：访问强化和软遗忘具体是什么关系？

只有真正注入 Agent 上下文的记忆才更新最后访问时间和访问次数。软遗忘会跳过高重要性、经常访问、存在冲突或属于画像的记录，只归档长期未触达的弱记忆。因此访问强化主要体现为“延长可用生命周期”，而不是简单粗暴地给相关性加分。

### 问题 7：长期记忆与上下文摘要有什么区别？

长期记忆面向跨会话复用，只保存经过筛选的稳定事实；上下文摘要面向当前运行，保存本次任务的目标、决策、证据进展和未解决问题。前者按用户和项目持久化，后者随 Query 运行状态持久化，不能互相替代。

### 问题 8：上下文压缩会不会破坏工具调用或丢失关键约束？

系统消息和完整研究摘要始终作为保护区，不参与压缩；最近消息按 Token 预算原样保留。切分点如果落在 Tool Message 上，会向前找到对应 AI Tool Call，一起保留。较早内容的摘要提示还明确要求保留用户目标、约束、决策、证据和开放问题。

### 问题 9：Mem0 不可用会不会导致整次研究失败？

默认不会。记忆是增强能力，不是研究主链路的单点依赖。初始化、召回、写入或维护失败时会记录失败和降级指标，并继续完成报告；如果业务要求严格一致性，也可以关闭 `memory_fail_open`，让写入错误显式暴露。

### 问题 10：如何衡量这套设计是否真正产生业务价值？

可以关注跨会话偏好命中率、有效召回采纳率、冲突或陈旧记忆误用率、用户重复说明背景的次数、上下文压缩前后 Token 量、记忆服务延迟和失败降级率。长期目标不是记得越多越好，而是在更低上下文成本下召回更少但更可信的信息。
